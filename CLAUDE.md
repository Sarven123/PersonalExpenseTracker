# PersonalExpenseTracker

## Project Overview
A private, local-only personal expense tracker for macOS, written in Swift 6 / SwiftUI / SwiftData / Swift Charts. Single-user, single-Mac, no accounts, no cloud sync, no analytics, no network calls. Primary bank source is Sparkasse (Germany); currency is EUR with German date/number conventions. UI language is English. Deployment target is macOS 14+. The codebase is deliberately split into a platform-agnostic Swift package (`Core/`, product `PETCore`) and a thin macOS app shell (`App/macOS/`) so an iOS target can be added later with minimal rework.

Was built in 8 phases, one phase per work session (the original phase plan is kept outside this repo, in the local Claude Code plans directory, since it is session/tooling metadata rather than project source). **All 8 phases of the original expense-tracker roadmap are complete as of 2026-09-20.** This file is the persistent handoff record between sessions — read it before doing any work, update it before ending any session.

**A second major feature arc — Net Worth / Investment Tracking (Phases 9–15) — began 2026-09-20**, extending the app beyond expense tracking into a personal net-worth/investment tracker (manual US stock/ETF holdings, physical gold, cash, liabilities) while keeping the existing expense Dashboard/Transactions/Insights untouched. This is the first change to relax the "no network calls, ever" invariant — narrowly, for manual-refresh-only market-data quotes, via a `com.apple.security.network.client` entitlement added only in Phase 12, not before. Full plan (schema design, provider research, phase-by-phase risk/acceptance breakdown) was written and approved via Claude Code's Plan Mode and is preserved at `/Users/REDACTED_USER/.claude/plans/pasted-content-id-ab8e-a-a-daki-s-r-m-swirling-wombat.md` — read that file for the full rationale behind any Net Worth design decision that seems under-explained here. See "Roadmap: Net Worth / Investment Tracking" below for phase status.

## Product Requirements
- Native macOS SwiftUI expense tracker, opened/run through Xcode.
- English UI; EUR currency; German date (DD.MM.YYYY) and decimal-comma number conventions by default.
- macOS 14+ deployment target; Swift 6; no third-party dependencies unless unavoidable.
- SwiftData for all local persistence; Swift Charts for interactive visualizations (hover tooltips).
- Sparkasse (Germany) CSV import: CSV-CAMT and CSV-MT940-style exports. No PDF import in v1. Resilient to semicolon delimiters, German decimal commas/thousands separators, UTF-8 and Windows-1252 encoding. Column-mapping + preview UI (layouts vary by region). Duplicate detection with a review step before commit. Never request bank credentials.
- Transactions: default categories (Food, Transport, Entertainment, Subscriptions, Housing, Utilities, Health, Shopping, Travel, Education, Fees, Income, Transfers, Other) plus user-created/custom categories (rename, recolor, manage). Transparent local rule-based category auto-suggestion. Recurring/subscription detection. Every field editable. Category corrections become local merchant rules. "Uncategorized" review filter. Transfers can be excluded from analytics.
- Manual entries: prominent "Add Expense" action, manual income too, appears identically to imported data everywhere.
- Dashboard: current-period total vs. prior period, interactive category donut/bar chart with hover tooltips, interactive time-series chart with hover, weekly summary (total/day-by-day/leading categories), recent transactions, top merchants, recurring/subscription summary, thoughtful empty state with opt-in (never automatic) demo data.
- Navigation: sidebar with Dashboard, Transactions, Insights, Settings, and (from Phase 10 onward) Net Worth. Filters (date range, month, week, category, merchant, type, source, transfers include/exclude) consistently affect every metric/chart/table. Searchable/sortable transaction table. CSV export of filtered transactions. Insights by category/merchant/month + subscriptions.
- Net Worth (Phases 9–15, in progress — see Roadmap below): manually-tracked personal net worth, kept strictly separate from expense tracking. Manual US stocks/ETFs (ticker, quantity, average purchase price, purchase currency, optional purchase date, fees) under average-cost accounting — no per-lot/FIFO tracking. One fixed physical-gold holding (11g, 995 purity) valued via a reference/spot price with dealer spread explicitly excluded. Manually-entered, timestamped cash balances and liabilities. `Net Worth = tracked assets + cash − liabilities`; shows "Tracked Assets" instead when cash/liability data is missing — this labeling applies retroactively on the historical chart too. Reporting currency is always EUR; USD-quoted assets convert via FX. Midas (the user's brokerage) is a manual-only account label, never an integration target — no credentials are ever requested for it, and no Midas API/scraper will ever be built. Market-data quotes (US equities/ETFs, FX, gold spot) are fetched only from free-tier providers, only via an explicit "Refresh Prices" button (never automatic/background), with Keychain-stored API keys and a manual-entry fallback always available. This is a tracking tool only — no trading, brokerage actions, or investment-advice language anywhere in its UI copy.
- Privacy: all data local via SwiftData, no unnecessary logging of sensitive content. No network calls anywhere in the expense-tracking feature set; the Net Worth feature's Phase 12 introduces the app's first-ever network capability, narrowly scoped to manual-refresh-only market-data requests (see Roadmap below and Important Decisions). Settings: backup export, "Delete All Local Data" behind a confirmation dialog.
- Engineering quality: feature-based folders, README, unit tests for German parsing/CSV parsing/categorization/duplicate detection/summary calculations, must build and test clean via `xcodebuild`.
- Future iPhone/iOS extensibility: shared logic and views isolated from macOS-specific chrome.

**SwiftData schema (implemented in `Core/Sources/PETModels`):**
- `ExpenseCategory` — id, name, colorHex, symbolName, sortOrder, isTransferCategory, isSystemDefault, createdAt; relationships to `transactions` and `merchantRules`. **Named `ExpenseCategory`, not `Category`** — see Important Decisions.
- `ExpenseTransaction` — id, bookingDate, valueDate?, amount (Decimal, signed), currencyCode, type (.expense/.income/.transfer), merchant, rawDescription (original bank text preserved), purpose?, bookingText?, iban?, counterpartyIBAN?, notes?, isRecurring, source (.manual/.imported), isExcludedFromAnalytics, dedupeHash, categorySuggestionSource?, createdAt, modifiedAt; relationships to `category`, `importBatch`, `recurringSchedule`. **Named `ExpenseTransaction`, not `Transaction`** — see Important Decisions.
- `RecurringSchedule` — id, frequency, interval, startDate, endDate?, dayOfMonth?, nextExpectedDate?, isActive; relationship to `transaction`.
- `MerchantRule` — id, matchType, pattern, priority, origin (.builtIn/.userCorrection), isRecurringHint, matchCount, createdAt; relationship to `category`.
- `ImportBatch` — id, importedAt, sourceFileName, sourceFormat, detectedEncoding, columnMapping (Data/JSON), rowCount, importedCount, skippedDuplicateCount, notes?; relationship to `transactions`.
- Delete rules: Category→Transaction `.nullify`, ImportBatch→Transaction `.nullify`, MerchantRule→Category `.nullify` (never cascade-delete spending data).
- `ModelContainerFactory` provides `makeLiveContainer()`, `makeInMemoryContainer()` (each call gets a uniquely-named in-memory configuration — see Important Decisions), `previewContainer`. Since Phase 9, both build via `ModelContainer(for:migrationPlan:configurations:)` using `PETMigrationPlan` — see Migrations below.

**Net Worth schema additions (Phase 9, `Core/Sources/PETModels`, all `.nullify` relationships, same wide-optional-fields-on-one-model convention as `ExpenseTransaction` rather than subclassing):**
- `InvestmentAccount` — id, name, notes?, isArchived, createdAt; relationship to `holdings`. Deliberately carries no credential/provider-link field — structurally cannot become a Midas-scraper integration point without an actual model change.
- `Holding` — id, assetType (`.usEquity`/`.physicalGold`), ticker? (nil for gold), displayName?, quantity (shares or grams), purityPerMille? (995 for the tracked gold instance), averageCostPerUnit, purchaseCurrencyCode, firstPurchaseDate?, totalFeesPaidEUR, manualCurrentPricePerUnit?/manualCurrentPriceAsOf? (always-available zero-network fallback), soldQuantity, realizedGainEUR, isArchived, notes?, createdAt, modifiedAt; relationships to `account` and `activities`. **`quantity`/`averageCostPerUnit` must only ever be mutated by a repository's `recordBuy`/`recordSell` (Phase 10) — never by a plain edit** — mirrors how only `TransactionRepository` may mutate `ExpenseTransaction.amount`.
- `HoldingActivity` — append-only audit ledger for buy/sell/fee events; id, activityType (`.buy`/`.sell`/`.feeOnly`/`.correction`), date, quantity?, pricePerUnit?, currencyCode?, feeAmount?, resultingQuantity, resultingAverageCost (state snapshots after applying this activity, so the ledger is self-auditing without replaying history), realizedGainEUR? (populated only on `.sell`, approximate under average-cost accounting), notes?, createdAt; relationship to `holding`.
- `BalanceAccount` — collapses cash and liability accounts via a `kind` enum (`.cash`/`.liability`) rather than two models; id, name, kind, currencyCode, isArchived, createdAt; relationship to `snapshots`.
- `BalanceSnapshot` — a timestamped, user-typed balance; id, amount, asOfDate, notes?, createdAt; relationship to `account`.
- `SecurityPricePoint` — cache **and** historical-backfill store for equity/ETF prices, one row per `(ticker, priceDate)` (uniqueness enforced in repository code, not the schema, mirroring `ExpenseTransaction.dedupeHash`'s code-level dedup); id, ticker, priceDate, closePrice, currencyCode (always USD), fetchedAt, source, isBackfilled.
- `FXRatePoint` — cache/backfill for FX rates; id, baseCurrency, quoteCurrency (always EUR), rateDate, rate, fetchedAt, source. Source is never silently mixed between providers for the same date (Frankfurter preferred, Alpha-Vantage-FX only as a fallback).
- `GoldPricePoint` — cache/backfill for gold spot, **always priced in USD** (never let the gold provider do its own EUR conversion — gold and equities must share exactly one FX pipeline, not two independent unaudited ones); id, priceDate, pricePerTroyOunce, currencyCode, fetchedAt, source, isBackfilled.
- Deliberately **not** a model: a `NetWorthSnapshot`/history table. The historical Net Worth curve will be *computed* by a pure `NetWorthCalculator` enum (Phase 11+, `Core/Sources/PETRepositories/NetWorth/`) over already-fetched arrays, following the `AnalyticsCalculator` precedent exactly — no `ModelContext` needed, trivially unit-testable.

**Migrations (Phase 9, `Core/Sources/PETModels/Migrations/`) — this app's first-ever `VersionedSchema`/`SchemaMigrationPlan`:**
- `SchemaV1` — a retroactive label on the exact five models this app has shipped since Phase 1, unmodified. Not a new shape; exists only so `SchemaV2` has something explicit to migrate from.
- `SchemaV2` — `SchemaV1.models` plus the eight new Net Worth models above. Purely additive — no existing model's attributes, types, or relationships change.
- `PETMigrationPlan` — `stages = [.lightweight(fromVersion: SchemaV1.self, toVersion: SchemaV2.self)]`. Pure addition qualifies for SwiftData's automatic lightweight migration; no custom `willMigrate`/`didMigrate` closures needed.
- Verified (see Phase 9 below) with an automated test that builds a real on-disk SQLite store using only `SchemaV1`, seeds it with data, then reopens that same file through `PETMigrationPlan` and confirms the original data survives and the eight new tables exist empty — a stronger, repeatable substitute for "manually copy a pre-existing populated store," since it exercises the same on-disk migration path SwiftData would use for a real user's store.

**Categorization (`Core/Sources/PETCategorization`):**
- `DefaultCategorySeed.all` — the 14 default categories (Food, Transport, Entertainment, Subscriptions, Housing, Utilities, Health, Shopping, Travel, Education, Fees, Income, Transfers, Other) with color/symbol/sortOrder; `Transfers` is the one `isTransferCategory` entry. Seeded automatically on app launch via `CategoryRepository.seedDefaultCategoriesIfNeeded()` (idempotent).
- `MerchantNormalizer.normalize(_:)` (Phase 5) — lowercases, drops a CAMT purpose field's trailing `//City/Country`, replaces punctuation with spaces, and strips common legal-entity suffixes (GmbH, AG, SE, KG, BV, Ltd, ...) so "REWE Markt GmbH" and "REWE SAGT DANKE//München/DE" both normalize to text containing "rewe".
- `CategoryRuleEngine.suggestCategory(merchant:purpose:rules:)` (Phase 5) — pure function matching normalized merchant+purpose text against a `[MerchantRule]` list by `matchType` (`.contains`/`.exact`/`.startsWith`/`.regex` — regex matches the *raw*, non-normalized text since normalization would mangle regex metacharacters), trying rules in descending `priority` order and returning the first hit's category.
- `BuiltInMerchantRuleSeed.all` (Phase 5) — ~40 starter rules for common German merchants (REWE/EDEKA/ALDI → Food, Netflix/Spotify → Subscriptions, DB Vertrieb → Transport, Stadtwerke → Utilities, Gehalt → Income, "eigenes sparkonto"/Umbuchung → Transfers, etc.), each targeting a `DefaultCategorySeed` category name by string.
- `RecurringDetector.detectGroups(in:)` (Phase 5) — groups transactions by normalized merchant; a group of 3+ with consistent amounts (within 10%) and a consistent booking-date interval (weekly/biweekly/monthly/quarterly/yearly bands) becomes a `RecurringGroup`. Purely additive by design — callers should only ever *set* `isRecurring`/attach a schedule from the result, never clear a flag a user set.

**Repositories (`Core/Sources/PETRepositories`, all `@MainActor`):**
- `CategoryRepository` — `fetchAll()`, `seedDefaultCategoriesIfNeeded()`, `create/rename/recolor/setSymbol`, `delete(_:reassigningTransactionsTo:)` (rejects deleting a system-default category via `CategoryRepositoryError.cannotDeleteSystemDefault`; rejects duplicate names case-insensitively via `.duplicateName`).
- `TransactionRepository` — `fetchAll(sortedByDateDescending:)`, `createManualTransaction(...)`, `update(...)`, `delete(...)`. Callers pass a positive `magnitude`; the repository derives the signed `amount` from `TransactionType` (expense/transfer → negative, income → positive) — see Important Decisions. Since Phase 5, whenever `create`/`update` is called with a non-nil `category`, it also calls `MerchantRuleRepository.recordUserCorrection(merchant:category:)` — "category corrections become local merchant rules" per the product spec.
- `ImportRepository` (depends on `PETImport` + `PETCategorization`) — `existingDedupeHashes()`, and `commitImport(sourceFileName:columnMapping:detectedEncoding:totalRowCount:acceptedDrafts:skippedDuplicateCount:)` which creates one `ImportBatch` (serializing the `ColumnMapping` to JSON) plus one `ExpenseTransaction` per accepted `DraftTransaction`. Since Phase 5, each transaction's category is auto-suggested via `CategoryRuleEngine` against every stored `MerchantRule` (`categorySuggestionSource` records `"rule:builtIn"`/`"rule:userCorrection"`; a draft with no matching rule stays Uncategorized), the winning rule's `matchCount` is incremented, and `RecurringScheduleRepository.refreshDetectedRecurrence()` runs once at the end of the commit.
- `MerchantRuleRepository` (Phase 5) — `fetchAll()`, `seedBuiltInRulesIfNeeded()` (idempotent — resolves `BuiltInMerchantRuleSeed` entries against real `ExpenseCategory` rows by name, skipping any whose category doesn't exist yet), `suggestCategory(merchant:purpose:)`, `recordUserCorrection(merchant:category:)` (creates a new `.exact`/`.userCorrection` rule at `priority: 100`, or bumps `matchCount` and re-points an existing one — no-ops for a merchant that normalizes to an empty pattern), `delete(_:)`.
- `RecurringScheduleRepository` (Phase 5) — `refreshDetectedRecurrence()` fetches every transaction, runs `RecurringDetector`, sets `isRecurring = true` on every transaction in a detected group, and attaches/updates a single `RecurringSchedule` on the group's most recent ("anchor") transaction with a computed `nextExpectedDate`.
- `DemoDataRepository` (Phase 6) — `seedDemoData(referenceDate:)`, inserted only from the Dashboard's empty-state "Load Demo Data" button (never automatically, per the product spec). Inserts ~24 clearly-fictional transactions (merchants named "Sample ...") spanning the last ~2 months across most default categories, including a few repeated-monthly patterns (rent, a streaming subscription, a transit pass) so `RecurringScheduleRepository` has something to detect. Bypasses `TransactionRepository` (inserts `ExpenseTransaction`s directly via the context) specifically so these fictional merchant names never create real `MerchantRule`s.
- `DataResetRepository` (Phase 7) — `deleteAllData()`, backing Settings' "Delete All Local Data" action. Batch-deletes every `ExpenseTransaction`/`RecurringSchedule`/`MerchantRule`/`ImportBatch`/`ExpenseCategory` via `context.delete(model:)`, then immediately re-seeds default categories + builtin merchant rules so the app stays usable without a relaunch.

**Analytics (Phase 6, `Core/Sources/PETRepositories/Analytics/AnalyticsCalculator.swift`):** a stateless enum of pure aggregation functions over an already-fetched `[ExpenseTransaction]` array — no SwiftData context needed, so (like `CategoryRuleEngine`/`RecurringDetector` in Phase 5) it's directly unit-testable and cheap to recompute reactively. `total(of:in:types:excludeTransfers:)`, `monthlyOverview(transactions:currentRange:priorRange:)` (current vs. prior period + percent change, `nil` when the prior period had no spending), `categoryBreakdown(transactions:in:)` → `[CategoryTotal]` (sorted descending, "Uncategorized" grouped as its own bucket), `dailyTotals(transactions:in:calendar:)` → `[DailyTotal]` for the time-series chart, `topMerchants(transactions:in:limit:)`, `weeklySummary(transactions:containing:calendar:)`, `recurringSummary(transactions:)` → active `RecurringSchedule`s only, soonest `nextExpectedDate` first, and (Phase 7) `monthlyTotals(transactions:monthsBack:referenceDate:calendar:)` → `[MonthlyTotal]` for Insights' 12-month trend chart. Every aggregation excludes `isExcludedFromAnalytics` transactions and (by default) transactions in a `Transfers`-flagged category. Deliberately **not** a `@MainActor` "AnalyticsRepository" class wrapping a fetch — see Important Decisions for why `DashboardView`/`InsightsView` call it directly against their own `@Query`.

**Filtering (Phase 7, `Core/Sources/PETRepositories/Filtering/FilterCriteria.swift`):** a pure, `Equatable` value type — date range (`.allTime`/`.thisWeek`/`.thisMonth`/`.custom(start:end:)`), a `Set<UUID>` of category IDs (against `ExpenseCategory.id`, **not** `persistentModelID` — see Important Decisions), `uncategorizedOnly`, `merchantSearchText`, `types: Set<TransactionType>`, `sources: Set<TransactionSource>`, `excludeTransfers`. `matches(_:calendar:referenceDate:)` is the combined predicate; `matchesAttributes(_:)` is every dimension *except* date range, used where a caller needs to filter by everything but intentionally ignore the date range (Insights' 12-month trend chart). `isActive` drives the filter-icon badge in the UI; `reset()` restores defaults. Shared by `TransactionListView` and `InsightsView` via the same `FilterPopoverView`, so filtering behaves identically wherever it appears.

**Shared UI (`Core/Sources/PETSharedUI`, pure SwiftUI, no AppKit):** `TransactionListView` (Phase 7 — now a searchable/sortable `Table`, see below), `TransactionEditView` (Add/Edit sheet, `.create`/`.edit(ExpenseTransaction)` modes), `CategoryManagerView` (create/rename/recolor/delete-with-reassignment), `ImportCSVView` (Phase 4 import wizard, see below), `MerchantRuleManagerView` (Phase 5 — lists rules grouped "Your Rules"/"Built-in Rules", only user-correction rules are deletable, mirroring built-in-category protection), `DashboardView` (Phase 6, see below), `InsightsView`/`SettingsView`/`FilterPopoverView`/`CSVDocument` (Phase 7, see below), `CategoryBadge`, `Color(hex:)`/`.toHex()` helpers, and `.petRequestAddExpense`/`.petRequestImportCSV` notifications. These views are platform-agnostic by construction so an iOS target can reuse them.

**Dashboard (Phase 6, `DashboardView` in `Core/Sources/PETSharedUI`):** owns its own `@Query(sort: \.bookingDate, order: .reverse) private var transactions`, computes everything else as `AnalyticsCalculator` calls over that array (all scoped to the current-vs-prior *calendar month*, with `@State private var referenceDate` as the seam for a future "pick a period" control). Sections: current-month total vs. prior month with a percent-change badge (red = spending rose, green = fell); a category-breakdown donut (`SectorMark` + `.chartAngleSelection(value: $selectedAngle)`, mapping the raw selected `Decimal` back to a category by walking cumulative sums — the standard Swift Charts recipe for a stacked/pie selection — plus a legend list) with hover tooltip; a daily-spending time-series (`LineMark`/`AreaMark` + `.chartXSelection(value: $selectedDay)` + a `RuleMark` annotation) with hover tooltip; a this-week bar chart + leading-category chips; recent transactions; top merchants; and a recurring/subscriptions list (from `AnalyticsCalculator.recurringSummary`). Empty state (no transactions at all) offers **only** an opt-in "Load Demo Data" button (via `DemoDataRepository`) — never automatic, per the product spec. **Dashboard was deliberately left as-is in Phase 7** (still current-month-only, no `FilterCriteria` integration) — see Important Decisions.

**Transactions (Phase 7 rewrite, `TransactionListView`):** now a `Table` (was a plain `List`) with sortable Date/Merchant/Amount columns (`sortOrder: Binding<[KeyPathComparator<ExpenseTransaction>]>`) plus non-sortable Category/Source columns; `.searchable(text: $filter.merchantSearchText)` doubles as both "search" and the merchant-filter dimension; a toolbar filter button (badge-filled icon when `filter.isActive`) opens `FilterPopoverView` in a `.popover`; multi-row selection (`Set<UUID>`, keyed off each model's own `id` property — **not** `PersistentIdentifier`, see Important Decisions) with a right-click context menu (Edit…/Delete) and double-click-to-edit via `.contextMenu(forSelectionType:menu:primaryAction:)`'s `primaryAction`; Delete key support via `.onDeleteCommand`; and an "Export CSV" toolbar button exporting exactly the currently filtered/searched rows via `TransactionCSVExporter`. The former dedicated "Uncategorized Only" quick-toggle was folded into the general filter popover (one extra click, but one consistent filtering system) — see Important Decisions.

**Insights (Phase 7, `InsightsView` in `Core/Sources/PETSharedUI`):** its own `@Query` + its own `FilterCriteria` + the same `FilterPopoverView` as Transactions. Sections: by-category (horizontal `BarMark` breakdown via `AnalyticsCalculator.categoryBreakdown`), by-merchant (top 10 via `topMerchants`), by-month (a 12-month `BarMark` trend via the new `AnalyticsCalculator.monthlyTotals`, deliberately filtered via `FilterCriteria.matchesAttributes` — ignoring the date range, since a "trend over time" chart and a fixed date-range filter are in tension), and subscriptions (`recurringSummary`). Category/merchant sections pass an all-encompassing `Date.distantPast..<Date.distantFuture` range into `AnalyticsCalculator` since date-range filtering already happened via `FilterCriteria.matches` beforehand.

**Settings (Phase 7, `SettingsView` in `Core/Sources/PETSharedUI`):** two sections — "Backup" (Export All Transactions as CSV, unfiltered, via the same `TransactionCSVExporter`/`.fileExporter`/`CSVDocument` machinery as Transactions' export) and "Danger Zone" (Delete All Local Data, behind a `.confirmationDialog` naming the exact consequence, calling `DataResetRepository.deleteAllData()`).

**Export (Phase 7, `Core/Sources/PETExport`):** `GermanExportFormatters` (the export-direction counterpart to Phase 3's `GermanDateParser`/`GermanNumberParser` — `formatDate` uses a fixed UTC calendar so a value round-trips to the same calendar day regardless of host time zone; `formatAmount` uses `Decimal.FormatStyle` with the `de_DE` locale) and `TransactionCSVExporter` (English column headers matching the app's UI language, German-formatted date/amount values, RFC 4180 quote-escaping, a `\r\n`-joined body, and a UTF-8 BOM prefix on `exportData(_:)` for maximum spreadsheet-app compatibility — deliberately not meant to be re-imported through the Sparkasse-specific `CSVImportPipeline`, this is a general data-export/backup format). `CSVDocument` (`PETSharedUI`) is a minimal `FileDocument` wrapper so `.fileExporter` can be used without AppKit.

**Import pipeline (Phase 3, in `Core/Sources/PETImport`):** `CSVImportPipeline.parse(fileData:)` is the single entry point — decodes bytes (`EncodingDetector`: UTF-8, UTF-8-with-BOM, or Windows-1252 fallback), splits into rows with a quote-aware semicolon `CSVParser` (handles doubled-quote escaping and a delimiter embedded inside a quoted field), detects which known Sparkasse layout the header row matches (`ColumnMapping.detect`, CAMT vs. MT940-style — the two layouts reuse the header label "Buchungstext" for different semantic roles, so detection is layout-aware, not a single flat alias table), then maps each row (`ImportRowMapper`) into a `DraftTransaction` using `GermanDateParser`/`GermanNumberParser`. Malformed individual rows become collected `ImportError` warnings rather than aborting the whole import. `DuplicateDetector` computes a SHA-256 `dedupeHash` per draft and partitions a batch into unique vs. duplicate against a caller-supplied set of existing hashes. `ColumnMapping`/`SemanticField` are `Codable` (Phase 4 persists the detected mapping into `ImportBatch.columnMapping`). Transaction type (expense vs. income) is derived purely from the amount's sign; recognizing transfers between the user's own accounts is not attempted here — Phase 5's rule-based category suggestion can still tag such rows with the "Transfers" *category* (e.g. via the built-in "eigenes sparkonto"/"umbuchung" rules) independently of `TransactionType`, see Important Decisions.

**Import UI (Phase 4, `ImportCSVView` in `Core/Sources/PETSharedUI`):** a 4-step sheet wizard — (1) `.fileImporter` file picker, (2) parse review showing detected format/encoding, any `ImportError` warnings, and a preview list of every parsed `DraftTransaction`, (3) duplicate review — fetches `ImportRepository.existingDedupeHashes()`, partitions via `DuplicateDetector.partition`, shows duplicates with a per-row toggle to force-include one anyway (skipped by default), (4) commit via `ImportRepository.commitImport(...)` and a completion summary. Reachable from `TransactionListView`'s toolbar, its empty state, or Cmd+I. Every step's actions (Cancel/Back/Continue/Import N/Done) live in a single per-step `.toolbar` — see Important Decisions for a real layout bug this fixed. The column-mapping step is **read-only** in v1 (see Important Decisions/Known Issues). As of Phase 5, imported transactions are no longer always Uncategorized — see Categorization above.

## Important Decisions
- **Renamed `Category` → `ExpenseCategory`.** Reason: `Category` collides with the Objective-C runtime's own `Category` typedef (`objc/runtime.h`), causing a real "ambiguous for type lookup" compile error once both Foundation/ObjC interop and the model module are visible together (hit this in the Phase 1 test target). Renaming once, early, avoids qualifying every reference throughout the whole app forever.
- **Core logic lives in a local Swift Package (`Core/`, product `PETCore`), not directly in the `.xcodeproj`.** Reason: SwiftPM auto-discovers new `.swift` files added to an existing target's `Sources/` folder, so most future phases won't require hand-editing `project.pbxproj` at all — only the thin `App/macOS` shell and `PersonalExpenseTrackerTests` need pbxproj entries when new files are added there. This was an explicit user-approved tradeoff over using `xcodegen` or a from-scratch GUI-created project.
- **`.xcodeproj` was hand-authored via a one-off generator script (not committed) using deterministic sha1-derived object IDs**, then validated with `plutil -lint` and `xcodebuild -list` before any build was attempted. If the pbxproj needs regenerating wholesale in a future session, prefer targeted `Edit` calls to add new file/build-file entries rather than regenerating the whole file, to avoid clobbering settings added in later phases.
- **Code signing set to ad hoc (`CODE_SIGN_IDENTITY = "-"`, `CODE_SIGN_STYLE = Automatic`, no team).** Reason: this is a personal, non-distributed app; matches Xcode's own "Sign to Run Locally" default and lets `xcodebuild` build/test/run without an Apple Developer account.
- **App Sandbox is on; no network entitlement is present at all, ever.** Reason: architecturally enforces the "no network calls" requirement rather than relying on code discipline alone. The user-selected-file entitlement started as `com.apple.security.files.user-selected.read-only` (Phase 1) and was upgraded to `com.apple.security.files.user-selected.read-write` in Phase 7 once CSV export needed `.fileExporter` — see the "Xcode project mechanics" paragraph above for that change's own reasoning. The absence of any network entitlement has never changed.
- **Swift Testing framework (`import Testing`, `@Suite`/`@Test`) used instead of XCTest** for both the package tests and the app-level test target. Reason: it's the modern, Xcode-16+-native testing framework and works identically in `swift test` and `xcodebuild test`; XCTest remains available if a future phase needs UI-hosted tests that specifically require it.

### Net Worth roadmap decisions (Phase 9 onward)
- **`VersionedSchema`/`SchemaMigrationPlan` introduced for the first time in Phase 9, exactly when the first schema change since Phase 1 was needed.** Reason: the original five models were shipped without any migration machinery at all (a plain `Schema([...])` literal); rather than keep deferring migration discipline to "whenever it's actually needed," Phase 9 established it at the safest possible moment — a purely additive change (eight new tables, zero changes to any existing model). `SchemaV1` is a retroactive, unmodified label on the shape this app has shipped since Phase 1; `SchemaV2` is `SchemaV1` plus the new Net Worth models; the migration stage is `.lightweight` (no custom `willMigrate`/`didMigrate` closures needed for a pure addition). Any future schema change (including within the Net Worth roadmap itself) should add a `SchemaV3` and a new stage rather than editing `SchemaV1`/`SchemaV2` in place.
- **The Phase 9 migration was verified with an automated test (`SchemaMigrationTests.migratesExistingDataWithoutLoss`) that builds a real on-disk SQLite store using only `SchemaV1.models`, seeds it with a category + transaction, then reopens that exact file through `ModelContainer(for:migrationPlan:configurations:)` and asserts the original data survived and the eight new tables exist empty — rather than relying only on fresh in-memory containers (which would never actually exercise a migration).** Reason: this is the first migration this app has ever needed, and the risk that mattered most was "does a real user's existing store survive," not "does a brand-new store initialize correctly" (fresh containers were already covered by every prior phase's tests). This on-disk round-trip test is a repeatable substitute for manually copying a real pre-existing populated store between builds, and should be the template for verifying every future migration stage this app adds.
- **`Holding`/`BalanceAccount` use the established "wide optional fields on one model, enum discriminator" convention (`assetType`/`kind`) instead of a class hierarchy for variants (stock vs. gold; cash vs. liability).** Reason: this mirrors how `ExpenseTransaction` already carries many type-conditional optional fields (`purpose`, `bookingText`, `iban`, etc.) rather than subclassing per transaction type — SwiftData's `@Model` classes don't support the kind of clean inheritance that would make a class hierarchy worthwhile here, and one flat model per concept keeps fetch descriptors, relationships, and repository code simple.
- **`Holding.quantity`/`averageCostPerUnit` are documented (in code comments and here) as mutable only via a repository's `recordBuy`/`recordSell` methods (Phase 10), never via a plain "edit holding" action, even though nothing in the Phase 9 schema itself enforces this at compile time.** Reason: average-cost accounting requires every quantity/cost change to also append a `HoldingActivity` audit row and correctly recompute `averageCostPerUnit`/`realizedGainEUR` — allowing a silent direct edit would let those fields drift out of sync with the audit ledger. This mirrors the existing precedent of `TransactionRepository` being the only path that mutates `ExpenseTransaction.amount`. Phase 10 must enforce this at the repository API surface (no public setter for those two fields outside `recordBuy`/`recordSell`), not just by convention.
- **`SecurityPricePoint`/`GoldPricePoint` do not use a compound-unique `@Attribute` for `(ticker, priceDate)` — uniqueness is left to be enforced in repository code before insert (Phase 12/13), same as `ExpenseTransaction.dedupeHash`'s existing code-level dedup.** Reason: SwiftData does not cleanly support compound-unique attributes across two properties; a single-property `@Attribute(.unique)` only works on `id`. This is a known, accepted gap until the repository layer that writes these rows exists.
- **`GoldPricePoint.currencyCode` is always `"USD"` — gold price fetches must never be converted to EUR by the market-data provider itself.** Reason: gold and equities must share exactly one FX conversion pipeline (Frankfurter, with Alpha-Vantage-FX as fallback) so there is a single, auditable place where USD→EUR conversion happens; letting a gold API do its own EUR conversion would create a second, independent, unaudited conversion path for the same reporting currency — a realistic and easy-to-miss bug source flagged during this feature's design review.
- **Deliberately no `NetWorthSnapshot`/history model was added in Phase 9.** Reason: following the `AnalyticsCalculator` precedent from Phase 6 exactly, the historical Net Worth curve will be *computed* (Phase 11+, by a pure `NetWorthCalculator` enum over already-fetched arrays), not stored — avoiding a ninth model and keeping the computation trivially unit-testable with zero `ModelContext`, exactly like `dailyTotals`/`monthlyTotals` already work.
